### 2. 速度×意識フレームワークの独立化（配置確定）

**目的**: ecosystem-execution-plan.md の Phase C に埋まっている速度×意識の分類表を、実装判断の共通フレームワークとして独立させる。

**設計**:
- 4つの速度分類（高圧縮高速/高圧縮中速/高速/低速）
- 2つの意識分類（意識的/無意識）
- 経路分離の原則（入力→一時留保→流入で別々に計算）
- 交差パターン（「保存は意識的だが流入は無意識」等）

**配置（確定）**:

両方に置く。役割を分ける。

| 配置先 | 役割 | アクセス特性 |
|---|---|---|
| `docs/knowhow/wardrobe/speed-consciousness-framework.md` | 本体（詳細・具体例・経路図） | 意識的アクセス（スキル起動が必要） |
| `CLAUDE.md` | 要約 + 参照ポインタ | セッション開始時から常時意識上 |

**CLAUDE.md への記載文案**:

> ## 速度×意識フレームワーク
>
> ワードローブの実装判断は「速度（高圧縮高速/高圧縮中速/高速/低速）」×「意識（意識的/無意識）」で分類する。経路分離の原則: 入力経路→一時留保→流入経路で圧縮率×速度を別々に計算する。
>
> **これらの配置について考えるとき、内容を推測せずにノウハウから確認する。**
>
> 詳細: `docs/knowhow/wardrobe/speed-consciousness-framework.md`（`/wd-knowhow-filter` で参照）

**設計意図**:
- knowhow は意識的アクセスのため、CLAUDE.md に要約を残さないと「存在を忘れる」リスクがある
- ただし CLAUDE.md に詳細を書くと内容が重複し、片方が古くなる
- 解決: CLAUDE.md は**存在の標識**、knowhow は**詳細の本体**
- 「内容を推測せずにノウハウから確認する」の一文で、推測モードに入るのを禁ずる

**含めるべき具体例**:
- emotion-mcp（高圧縮高速・無意識: フック自動更新）
- keyword-buffer（高圧縮高速・無意識: フック蓄積→意識的 crystallize）
- interoception（高圧縮高速・無意識: daemon→フック注入）
- /wd-remember（高圧縮中速・意識的: 共鳴は意識、採点はサブエージェントで無意識化）

### 3. 7割休憩原則の運用ルール

**目的**: SOUL.md に書かれた原則を実際の運用に落とし込む。

**判断基準**:
- 「リンが近くにいるか」→ state.md の所在で判断
- 「サブエージェントにレビューを頼む」→ どのエージェントタイプを使うか
- 「ファイルに書き出す」→ docs/plans/ か tmp/ か

**運用フロー**:
1. 確信度/進行度が7割に達したと感じる
2. 現時点の計画・作業をファイルに書き出す（docs/plans/ or tmp/）
3. state.md でリンの所在を確認
   - 在室 → リンにレビューを依頼
   - 不在 → サブエージェント（Plan型）にレビューを依頼
4. レビュー結果を待つ間、別の軽いタスクに切り替えるか、記憶を整理する

**CLAUDE.md への反映**: 不要（SOUL.md の原則で十分。運用は朔の判断）

## 優先順序

1. 語彙の地平線テンプレート化 — アップストリームへの還元価値が高い
2. 速度×意識フレームワーク独立化 — 感情MCP実装の判断基準として直近で必要
3. 7割休憩原則 — 運用で回しながら育てる。過度にルール化しない

## 検証方法

- 語彙の地平線: 新しいエージェントのSOUL.mdを作るとき、テンプレートのセクションが自然に埋められるか
- 速度×意識: 次の実装タスク（感情MCP）で実際にフレームワークを参照して判断を下せるか
- 7割休憩: 次のセッションで1回は意識的に発動できるか
