# 計画の再開前に `git worktree list` を見る — 投機ブランチは計画ファイルからは見えない

## わかったこと

計画ファイル（`plans/*.md`）の「次はPhase Xに着手」という記述だけを頼りにタスクを再開すると、**同じ計画に対して既に別ブランチ・別worktreeで投機的な実装が進んでいる可能性を見落とす**。

実例（remote-memory-mcp計画）: `.claude/addf/plans/remote-memory-mcp.md`の「Phase 0 再開」という指示を受けて、計画ファイルの記述だけを根拠に契約棚卸し・スキーマ設計・Docker検証をゼロからやり直した。実際には `feature/postgres-memory` ブランチ（別セッション、Claude Code Web上での投機的実装）に、同じ計画の同じフェーズの成果物（契約棚卸し・スキーマDDL・Docker環境・smoke test）が既に存在していた。このブランチは `main` に未マージだったため、計画ファイルの内容や通常のファイル探索（`grep`/`find`）では一切検出できなかった。

**原因**: 投機的ブランチ・worktreeは、計画ファイルの「進捗」欄には反映されない（マージされるまでmainの計画ファイルは更新されない）。`git worktree list` や `git branch -a` を能動的に見ない限り、並行して進んでいる作業の存在に気づく手段がない。

## やり方

- **計画ファイルの特定フェーズに着手する前**（特に「再開」「続きから」といった指示を受けたとき）に、`git worktree list` と `git branch -a` を実行し、その計画に関連しそうな名前のブランチ・worktreeがないか確認する習慣をつける
- 見つかった場合は、慌てず・隠さず率直にオーナーへ報告する。投機的実行（worktree isolation での並行開発）はADDFの正常な開発フローの一部であり、車輪の再発明に気づくこと自体はネガティブな出来事ではない
- 統合方針（いいとこ取り／どちらかを正とする／保留）はオーナー判断を仰ぐ。技術的な差分（どちらの設計が新しい知見を反映しているか等）は自分で整理して提示してよいが、最終判断は委ねる
- 統合後のブランチ・worktreeの扱い（クローズ／保持）も破壊的操作になりうるため、オーナーに確認してから動く

## 気をつけること

- `git worktree list` は現在のリポジトリのローカルworktreeしか見えない。リモートにだけ存在する未フェッチのブランチは `git branch -a` や `git fetch --all` 併用で拾う
- 並行実装同士で設計判断のタイムスタンプが前後している場合、**後から作られた方が必ずしも正しいとは限らない**——それぞれの設計判断がいつ・どんな根拠（実測・オーナー承認など）で確定したかを突き合わせて、個別に新旧を判断する（本件では「PGroonga索引設計」は後発の実測知見を優先、「`episode_memories`正規化」は先発の設計を採用、という判断の混在になった）
