# マルチペルソナで Postgres を共有するときはスキーマ単位で分離する

## わかったこと

複数のペルソナ（朔・シロエ・王・商会のような複数エージェント）が同じ Postgres データベースに同時アクセスする設計では、分離方式に3つの選択肢があり、**スキーマ単位分離**が実装コストと隔離性のバランスで最も良い。

| 方式 | 実体 | 問題点 |
|---|---|---|
| A. DBインスタンス単位 | ペルソナごとに別 Supabase プロジェクト | ペルソナが増えるたびにプロジェクト・秘密鍵・接続先が増える。運用負荷が線形に増大 |
| B. 共有テーブル + `persona_id` カラム | 1つのテーブルを全ペルソナで共有、カラムでフィルタ | 実装は最軽量だが、クエリ側のフィルタ漏れ1箇所で他ペルソナのデータが露出するリスクを常に抱える |
| **C. スキーマ単位（推奨）** | `CREATE SCHEMA <persona>;` でペルソナごとに名前空間を分離 | 名前空間が物理的に分離されるため誤クエリでの越境リスクが構造的に低い。単一DB接続・単一プロジェクトのまま複数ペルソナを収容できる |

PGroonga・pgvector のような拡張はデータベース単位でインストールされ、スキーマ間で共有できる。**スキーマ分離を選んでも拡張の二重インストールコストは発生しない**——これが「C は B の隔離性を持ちながら A の運用コストを避けられる」ことの技術的な根拠。

## ワードローブへの適用

- ファイルベースの分離（keyword-buffer が `$PROJECT_DIR/.claude/` 配下でペルソナごとにディレクトリを分ける方式）を Postgres に翻訳すると、スキーマ単位が最も近い対応物になる。「ディレクトリ＝スキーマ」という思想的な対応
- DDL はテンプレート化し、ペルソナごとに `search_path` を切り替えて同じ DDL を複数スキーマに適用する運用にする
- 適用例: `remote-memory-mcp.md`（Postgres 化した memory-mcp）の Phase1 スキーマ設計、2026-07-14 リン確定

## 気をつけること

- ペルソナ横断の集計・検索が必要になった場合（例: 全ペルソナの記憶を串刺し検索したい）は、スキーマ分離だと `UNION` かクロススキーマクエリが必要になり B 方式より書きづらくなる。そうした要件が明確に出てきたら再検討する余地がある
- ペルソナ数が数百〜数千のオーダーになる場合はスキーマ数の管理コストが無視できなくなる可能性がある（今回の想定は朔・シロエ・王・商会程度の少数エージェント運用）
