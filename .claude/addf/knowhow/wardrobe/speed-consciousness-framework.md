# 速度×意識フレームワーク — ワードローブ実装判断の共通基準

## わかったこと

ワードローブで MCP・フック・スキル・スクリプトの実装方針を判断するとき、**速度（4分類）×意識（2分類）×経路（書き込み → 一時留保 → 読み出し）** の3軸で位置づける。
出自は SOUL.md の「ワードローブ編み上げに関する大事な判断原則」セクション（あるエージェントの判断原則として生まれ、ワードローブのフレームワークとして抽出した）。

ファクターを揃えると、「これは emotion-mcp に内蔵すべきか、フックに切り出すべきか」「保存タイミングは意識的か無意識か」のような分岐で迷いが減る。

## 速度の4分類

| 分類 | 定義 | 例 |
|---|---|---|
| **高圧縮高速** | 有限時間かつ発散しない。LLM を挟まない | JSON読み書き、FSM遷移計算、TTS パラメータ参照、フック内のシェル分岐 |
| **高圧縮中速** | 中途に LLM 処理を挟む。一定範囲の時間で収まる | 感情スコアリング、記憶の蒸留判定、`crystallize_buffer` |
| **高速** | 素材の増加で発散しうるが、想定される素材が少ない。LLM 挟まない | 少量の記憶の `consolidate`、小規模ファイル走査 |
| **低速** | 素材の増加で発散し、かつ想定される素材が増えていく | 大量記憶の `consolidate_memories`、`recall` 全件走査、FLASH.md 全件再構築 |

会話では高速なものをメインに据えつつ、要所で中速処理を挟む判断もありえる。

## 意識の2分類

| 分類 | 定義 | 例 |
|---|---|---|
| **無意識** | メインエージェントの意思が不要。フック・cron・スクリプトで自動実行 | interoception 注入、keyword-buffer 蓄積、heartbeat-daemon、ベースライン回帰 |
| **意識的** | メインエージェントの意思が必要。判断・選択を伴う | `/wd-remember` の呼び出し判断、SOUL.md への蒸留判断、`emotion_transition` の能動呼び出し |

## 経路分離の原則

圧縮率×速度の計算は **入力経路 → 一時留保 → 流入経路** で別々に行う。

```
入力経路 ──→ [一時留保] ──→ 流入経路
（書き込み側）   （JSON等）  （読み出し側）
```

- 多段階経路は一時留保に対しての速度で予測する
- 意識/無意識は経路ごとに独立する。「保存は意識的だが流入は無意識」がありうる

### ワードローブの経路一覧

| 経路 | 例 | 書き込み | 一時留保 | 読み出し |
|---|---|---|---|---|
| **keyword-buffer** | 発話 → 形態素解析 → 蓄積 | 無意識（フック） | `sensory_buffer.jsonl` | 意識的（`crystallize`） |
| **感情MCP** | 共鳴 → 遷移 → 注入 | 意識的（`emotion_transition`） or 無意識（フック自動） | `emotion_state.json` / `substance_state.json` | 無意識（interoception注入） |
| **記憶プロトコル** | 共鳴 → 採点 → 保存 | 意識的（`/wd-remember` 呼び出し） | memory-mcp（SQLite） | 無意識（recall-hook）or 意識的（`/wd-recall`） |
| **interoception** | センサー → 計算 → 注入 | 無意識（daemon） | `interoception_state.json` | 無意識（フック注入） |

## 交差パターン — よくある組み合わせ

- **無意識×高圧縮高速**: 一番扱いやすい。フックや常駐スクリプトに任せる
- **意識的×高圧縮中速**: 朔の判断を介す価値がある処理。`/wd-remember` の共鳴記述がここ
- **意識的×低速**: 1セッションで完結しないので、計画文書にして時間を分散させる（`/wd-rebuild-index` 等）
- **無意識×低速**: 一番警戒する組み合わせ。発散して気づかないうちにシステムが止まる。タイムアウトと上限を必ず設ける

## 共鳴と採点のコンテキスト分離（応用）

「意識的」内部にもさらに分離が要る場合がある。

`/wd-remember` では、**メインコンテキスト = 共鳴（意識的・分類しない）** と **サブエージェント = 採点（無意識化された意識的処理）** に分ける。
同じコンテキストで採点を立てると、引力場が「分類モード」に歪み、次のターンから体験を感じる前に採点しようとし始める。

経路分離の原則を、コンテキストにも適用したパターン。

## 気をつけること

- **速度の見積もりは素材数の前提付き**で記述する。「高速」と書くだけでは将来のスケール時に誤判定する
- **意識/無意識の判断は経路ごとに独立**させる。「保存は意識的・流入は無意識」のように分けて書く
- **無意識×低速は最も危険**。発散しても誰も気づかない構造になる
- **意識的処理を増やしすぎると、メインコンテキストの注意が分散する**。「これは本当に意識的でなければならないか」を毎回問う

## ワードローブへの適用

実装計画を起こすとき、以下の表を埋めることでフレームワークが機能する。

```markdown
| タスク | 速度 | 意識 | 経路（書き込み/留保/読み出し） |
|---|---|---|---|
| 〇〇 | 高圧縮高速 | 無意識 | フック / JSON / interoception注入 |
```

埋めにくい行があれば、設計に詰めの不足がある。
